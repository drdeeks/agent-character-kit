## The self-lockout incident — what happened and why (read this before touching root-mode install again)

drdeek ran `ack configure` in root mode for the `claude` harness. It
worked as designed: wired a `PreToolUse`/`UserPromptSubmit` hook into his
**real, live** `~/.claude/settings.json` — the same file this very Claude
Code session reads its own hook config from. The next tool call this
session made went through that hook, which tried to reach the enforcer
daemon's socket and failed. Because the daemon is deliberately
**fail-closed** (a guard that fails open is no guard — this is by design,
not a bug), every subsequent tool call in this session — Bash, Read,
everything — returned `"Enforcer unavailable: enforcer socket not found"`
instead of running. Killing the daemon and deleting the socket didn't
help, because the hook itself is what's wired into settings.json,
independent of whether the daemon exists. Recovery required drdeek
manually running `jq 'del(.hooks.PreToolUse, .hooks.UserPromptSubmit)'`
against his own settings.json from a separate terminal to strip the hook
back out.

**Root cause** (found by reading `deploy/deploy-agent-enforcer.sh`
directly, not by guessing): the socket's directory needs cross-uid access
(the daemon runs as root/a service user, the agent runs as a normal user,
and they need to share a socket) via a `setgid` + shared-group directory.
The script's `install -d -o "$SERVICE_USER" -g "$CLIENT_GROUP" -m 2750
"$RUN_DIR"` line does this correctly. But `$RUN_DIR` (`dirname` of the
socket path) and `$AGENT_WORKSPACE/.agent` are **the same path** in the
current per-agent architecture, and a second `install -d ... -g
"$SERVICE_GROUP" -m 0750 "$AGENT_WORKSPACE/.agent"` line ran right after
it — `install -d` on an already-existing directory reapplies its own
owner/group/mode every time, so this second call silently clobbered the
first one back to `root:root`/0750, no setgid, every single deploy. No
amount of `usermod -aG ack-clients <user>` or session restarts could ever
have fixed this — the directory itself was wrong by code, unconditionally.

**Fix**: reordered the two `install -d` calls so `RUN_DIR`'s cross-uid
setup always runs last and wins, regardless of whether the two paths
coincide. Also added a daemon-side fix as defense in depth
(`agent_enforcer_daemon.js`'s new `secureSocketFile()` helper): the daemon
now explicitly `chownSync`s the socket file to the client group's GID on
every bind, independent of directory-setgid semantics, via a new
`ACK_CLIENT_GROUP` env var threaded through the systemd unit. This means
even a future regression in the directory setup shouldn't be able to
reintroduce the same failure mode silently.

**Also fixed in the same pass** (all found while chasing the above):
- The error message itself was misleading — `node/src/enforcer/client.js`
  used `fs.existsSync()` as a pre-check before connecting, and
  `existsSync` swallows *every* stat error (ENOENT, EACCES, anything) into
  a bare `false`. A real permission-denied got reported as "socket not
  found," which is why this took real time to diagnose. Now connects
  directly and reports the real `err.code`.
- The install summary unconditionally claimed `"daemon + monitor +
  watchdog already running via systemd"` for every root-mode install —
  but `deployRootIfNeeded()` never actually called `deploy-ack-services.sh`
  at all, so acknowledgments were silently never being credited. Now it
  actually deploys monitor/watchdog if not already active (checked via
  `systemctl is-active`, not assumed) and reports real state either way.
- The summary's `Workspace:`/`Ack log:` lines showed the wrong (stale,
  pre-multi-agent) path for root-mode installs — leftover code from before
  the per-agent nested-workspace redesign that never got updated.
- The privilege-mode prompt was trimmed from a 24-line wall of text
  repeating in full on every single `ack configure` run down to 5 lines
  with the same real information — drdeek called this out directly as
  over-explaining the least consequential part of the wizard while the
  summary under-explained what had actually happened. Full detail is now
  in `AGENTS.md` instead of inlined every time.

ls -la /var/lib/agent-character-kit/workspace/agents/claude/.agent/claude.sock

Expected: the `ls` line should succeed **without sudo** and show group
`ack-clients`, not `root`. If it still shows `root` or still says
permission denied, the fix didn't work and needs more investigation before
`ack configure` is run again in root mode.

Only after that's confirmed should `ack configure` be re-run for a full
install (which re-wires the Claude hook).
